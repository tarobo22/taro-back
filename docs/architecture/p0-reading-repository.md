# Reading v2 persistence boundary

`ReadingV2Service` now depends on `ReadingRepository`, `ReadingUnitOfWork` and `ReadingCatalog` protocols. It contains no SQL, psycopg import, Jsonb conversion, database row mapping or import from the AI application implementation. Card selection, version/state decisions, idempotency policy, timezone/day calculation, catalog checks and commit orchestration stay in the application/domain layers.

`PostgresReadingV2Repository` owns parameterized SQL, PostgreSQL owner advisory locks, the default owner lifecycle lookup, Jsonb serialization and conversion from database rows to typed `ReadingRecord`, `DailyAnchor` and `ReadingCommand` projections. The repository's prebuilt public reading view preserves the existing HTTP JSON shape, including hidden unselected cards and captured timezone/version values. A supplied owner-guard callback is invoked inside the adapter on the bound transaction.

`PostgresReadingV2UnitOfWork(pool)` exposes `readings` and explicit `commit()`. Its `repository_for(transaction)` constructs a repository over an existing opaque transaction without acquiring another connection or committing. The concrete adapter retains its connection property for compatibility, but the application UoW protocol does not expose a driver connection.

Constructor arguments and every public service/HTTP signature are unchanged. Existing AI/privacy/journal callbacks `snapshot`, `validate`, `mark_generating`, `mark_failed`, `complete`, `source_exists`, `export_owner` and `erase_owner` still accept their established transaction/owner arguments. Application callbacks immediately wrap the transaction through `repository_for`; they perform no driver operations. The opaque `repository.transaction` token is passed unchanged to the existing AI cancellation callback, retaining one atomic transaction across contexts. Both erasure call orders remain supported. Erasure/failed-state callbacks still work while the owner is deleting.

Daily anchors, source ownership, ordered slot selection, owner locks, version CAS, pagination, idempotency references, result validation and expiry semantics are preserved. The service treats a failed shuffle/selection CAS as the existing version-conflict response and does not remember or commit the operation. No API, schema, migration, domain selection rule or AI job implementation was changed in this extraction.

New unit tests use fake units of work with no connection or execute capability. They exercise anchor reuse, replay/deleted references, selection order/CAS misses, owner-state rejection, cancellation-before-deletion, bound-transaction callbacks and validated completion. Existing PostgreSQL reading and AI cancellation/erasure race tests remain unchanged and cover the actual adapter behavior. This is a focused persistence-boundary extraction, not a new aggregate/state-machine redesign or a claim that all future DDD decomposition is finished.
