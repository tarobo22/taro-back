# P0 data, catalog, and privacy integration

`DataPrivacyUseCases(uow_factory, policy, catalog, *, export_callbacks=(), erase_callbacks=(), feedback_target_exists=None, clock=None)` takes a `DataPolicy.from_mapping(shared/data-policy.json)` and the parsed immutable `shared/data-catalog.json`. Its constructor does not query the database. Use `lambda: PostgresDataPrivacyUnitOfWork(pool)` for the transaction factory.

`data_privacy_router(service, owner_dependency, *, status_owner_dependency=None)` registers only the owned `/v2` data/catalog/privacy operations. The composition root must include the router. `get_me(owner)` returns the specification's `Me`; `update_preferences(owner, patch)` validates the policy's locales, IANA timezone, tone, motion and voice mode. Locale changes affect the saved preference; this version's catalog meanings remain Korean. Python `zoneinfo` needs the `tzdata` package on systems without an OS timezone database.

Session creation can call `api.adapters.data_privacy_postgres.initialize_profile(connection, owner, locale, timezone)` in the same transaction that inserts `app_sessions`. The helper validates the same policy and never commits. `owner_guard(connection, owner) -> bool` requires an existing session and active lifecycle; a legacy session with no profile is active. `lock_owner(connection, owner)` acquires `pg_advisory_xact_lock(hashtextextended('yeoun:owner:{owner}',0))`. Every sensitive writer, including AI final commits, must use that lock and guard in its final transaction.

`list_decks() -> {items, next_cursor}`, `get_deck(UUID) -> Deck`, `list_cards(*, deck_id=None, arcana=None, suit=None) -> {items, next_cursor}`, and `get_card(int) -> Card` expose exact specification DTOs. The default deck ID is `fa221057-0567-5e10-8054-26661dac2e0a`; version `rws1909-20261105-ef03c0b150d3` derives from the existing source manifest. All 78 fronts and the back were compared with the existing local assets' SHA-256 and actual JPEG dimensions. The front assets are in the RN repository; the manifest's back was found in the supplied specification prototype. Asset URLs retain the source manifest's thumbnail URLs, with the original Commons source page and recorded license metadata.

HTTP catalog lists use `cursor` and policy-driven `limit` (default 20, range 1..50). Cursors bind the catalog kind, immutable source manifest and filters. `deck_version_id` is the canonical image-version query for list/detail; `deck_id` remains a list alias and conflicting values return 422. Domain callers that omit `limit` still receive the full catalog for reading selection. All 78 cards remain covered by the original exhaustive assertions, now aggregating both pages.

The existing manifest records `prototype_candidate`, so the deck remains `candidate`. This implementation does not claim independent rights approval or change asset publication status. The current prototype may explicitly select this known candidate; production publication needs the separate asset approval decision. Retired or unknown deck IDs must not be accepted for new draws.

Owned tables are `data_privacy_profiles`, `data_privacy_feedback`, and `data_privacy_requests`, created by migration `0007_p0_data_privacy.sql`. Migration `0020_data_privacy_receipt_salt.sql` adds private per-request receipt material; published migration 0007 is unchanged. Owner foreign keys cascade or detach on session cleanup, preserving existing fixture cleanup. No v1 route or table contract is replaced.

`create_feedback(owner, values, request_key)` persists app feedback or exactly one owned reading/turn target. The HTTP route requires a UUID `X-Idempotency-Key`; `Idempotency-Key` is an alias, and conflicting headers are rejected. Identical owner-scoped replays return the original response; changed payloads return 409. Input lengths and daily limits come from data-policy. The optional `feedback_target_exists(connection, owner, kind, target_id) -> bool` lets the composition root validate v2 reading/turn ownership in the same locked transaction. Without a callback, only legacy reading targets and targetless app feedback are supported; missing and other-owner targets both return 404.

## Private data jobs

`create_data_request(owner, kind, confirmation, request_key)` durably accepts a queued request. Erasure requires exactly `내 기록 모두 삭제` and changes the profile to `deleting` in the acceptance transaction. The HTTP response remains 202/queued while a FastAPI background task invokes `process_request(request_id)`. Acceptance is never presented as deletion completion. `process_pending(limit=20)` is the recovery entry point for queued/running rows after process interruption. The composition root or operational runner must invoke it on recovery; these modules do not start a background scheduler in their constructor. Failed jobs remain failed; an operator can explicitly retry the same `process_request` after resolving the cause.

`get_data_request(request_id, *, owner=None, receipt=None)` returns only the specification's minimal status. `status_owner_dependency` should return `None` when an `X-Data-Receipt` header is supplied and otherwise perform normal bearer authentication. This permits the exact receipt to poll after erasure revokes the old session. Wrong receipts and other-owner/missing IDs all return 404. Query parameters cannot authorize status. Receipts are HMAC capabilities bound to private random per-request material, request ID, owner, and request key; raw receipts and raw request keys are never stored. Identical authenticated replays derive the original receipt. The private material is removed from a completed detached erasure receipt.

`download_export(owner, request_id) -> bytes` always requires full owner authentication. The HTTP endpoint returns `application/zip`, an attachment filename and `Cache-Control: no-store`; a receipt alone grants no download access. There are no public export URLs, query credentials or export files in a web directory. The ZIP is stored privately in PostgreSQL and contains `manifest.json`, `data.json`, and per-collection CSV files. CSV cells that could execute spreadsheet formulas are escaped; the JSON preserves the original text. Export files expire after policy `exportFileHours` (24). Expired access removes the private bytes and returns 410. `purge_expired()` removes expired file bytes and detached receipts after policy `receiptDays` (30); it must be run by the operational recovery/maintenance runner to purge files that are never accessed again.

The base exporter includes the profile and the complete owned v1 journal/readings/daily/counsel/feedback data, without session token hashes, idempotency snapshots, job leases or receipts. Every `export_callbacks` entry is `(connection, owner) -> dict[str, collection]`, using the same owner-locked transaction. Contexts must return deliberate personal-data views, not raw SQL table dumps. Recursive filtering also removes credential/internal snapshot keys and rejects raw binary audio. Dataset names must be safe simple names and cannot replace an existing collection. Base names are `profile`, `journal_entries`, `readings`, `daily_readings`, `counsel_sessions`, and `feedback`; a v2 reading exporter should use a distinct name such as `v2_readings`. Each added collection must be an object or a list of objects for JSON and CSV portability.

Each `erase_callbacks` entry is `(connection, owner) -> None`, invoked under the owner lock after state has become `deleting`. The AI and v2 reading contexts must remove their personal records and invalidate pending work in this transaction. These callbacks must not require the owner to still be active. They must not commit the supplied connection. Privacy orchestration then removes v1 journals/readings/daily/counsel and retry snapshots, legacy pending AI jobs, all feedback and prior export requests/files. It replaces the old session token hash with unrelated random material, resets preferences, persists `erased`, and detaches the completed receipt (`owner_id`, idempotency digest, fingerprint, private receipt material and export bytes are all cleared). Minimal anonymous owner/usage tombstones remain so global quota accounting is not reset. Existing `ai_usage_attempts` are deliberately retained.

The entire sensitive completion, including all database erasure callbacks, commits together. A callback failure rolls back personal-data deletion, marks the request failed, leaves the profile deleting, and never reports completion. Only exception type names are logged. File deletion callbacks must be idempotent so an explicit retry is safe if external cleanup preceded a database rollback. Every provider result writer, including v1, must acquire the shared owner lock and recheck `owner_guard` in its final transaction; this is what prevents a late provider result from recreating erased data.
